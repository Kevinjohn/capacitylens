# How CapacityLens is tested

CapacityLens is alpha software with a single maintainer, so automated checks carry most of
the safety net. This page lists the suites and what each one covers. The
[development guide](/reference/development) has the commands, the enforced coverage floors
and the CI jobs.

Sizes below are approximate, counted once on 2026-10-01. No test enforces them, so they
will drift.

| Suite | Tool | Covers | Size (approximate) |
| --- | --- | --- | --- |
| App and shared unit tests | Vitest, Testing Library | The shared scheduling rules, the client store, and React components | About 310 test files |
| Server tests | Vitest | The API, authorisation, the SQLite database, migrations from released database fixtures, backups and sign-in | About 180 test files |
| End-to-end tests | Playwright | The demo, database-backed and password sign-in flows in a real browser | About 70 spec files |
| Accessibility checks | axe, inside the end-to-end tests | Automated accessibility rules on key screens | 7 spec files |
| Mutation testing | Stryker | Whether the unit tests fail when the scheduling logic is changed | Run on demand, not on every change |

## What each suite is for

- Unit and component tests cover the rules that decide who is over capacity, plus the
  screens that show the result.
- Server tests include released database fixtures. Each fixture is a database generated by
  that release's build, and the tests migrate a copy of it to the current schema. The oldest is from
  0.20.0-alpha.1.
- End-to-end tests run Chromium by default. WebKit and Firefox runs are opt-in.
- Axe finds common accessibility problems such as missing names and low contrast. It does not
  replace testing with assistive technology.
- Mutation testing covers the pure scheduling and helper code only. It does not measure the
  server or the React screens.
