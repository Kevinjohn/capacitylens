Architecture ​

This page is for contributors reading the code for the first time. It names the module that owns each capability, the transaction it runs in, where authority is checked, where the response is projected, and the tests that pin it. Product rules and framework departures are recorded in DECISIONS.md; naming and error rules are in Code standards. The page cites files, not line numbers.

Responsibility map ​

One planning write, end to end ​

Diana Prince's booking on the Themyscira rebrand changes from 4 to 6 hours a day. The browser sends one typed request:

http
PATCH /api/accounts/:accountId/allocations/:id
{ "mutationId": "<uuid>", "baseRevision": 41,
  "intent": { "operation": "allocation.update", "id": "<id>", "changes": { "hoursPerDay": 6 } } }

Two middleware gates run before the controller and can refuse:

  • P1. apps/backend/app/middleware/masquerade_read_only_middleware.ts (server stack) resolves view-as mode, requires the context header on unsafe methods (428 MASQUERADE_CONTEXT_REQUIRED) and refuses every unsafe request while viewing as another member (403 MASQUERADE_READ_ONLY).
  • P2. apps/backend/app/middleware/trusted_local_middleware.ts (router stack) returns 401 { error: 'Sign-in required.' } with no code when there is no valid session.

Then, in order:

  1. apps/backend/start/planning_routes.ts maps the route (api.planning.allocation.update) to PlanningController.allocationUpdate.
  2. apps/backend/app/controllers/planning_controller.ts validates the body with ctx.request.validateUsing(allocationMutationValidator) from apps/backend/app/validators/planning/allocation.ts.
  3. The controller's execute checks that the intent's operation equals the route's operation, that a catalogue intent names the route's entity, and that the target id equals the route id. A mismatch is VALIDATION_ERROR.
  4. mutatePlanning in apps/backend/app/services/planning.ts takes over.
  5. withActor (apps/backend/app/services/auth/current_actor.ts) opens the Account Kit withCurrent transaction. The Kit checks the session, credential revision and registry row under the account lock; the product then requires an active, confirmed, admitted account and binds the captured view-as context. Every later step uses this one transaction handle.
  6. currentAuthority resolves the effective principal (view-as re-check in apps/backend/app/services/auth/masquerade.ts), the live membership role (activeMembership in apps/backend/app/services/auth/authorization.ts), the Access Control Bouncer planning:read ability and the company row. canWrite is the planning:write ability, false under view-as.
  7. The write is refused unless canWrite holds.
  8. Idempotency: a row in planning_mutations with this mutationId means MUTATION_ID_REUSED.
  9. assertPlanningBaseRevision (apps/backend/app/services/planning_revision.ts) refuses a stale baseRevision with STALE_REVISION.
  10. Before image: readStateWithClient (apps/backend/app/services/state_repository.ts).
  11. executePlanningIntent (apps/backend/app/services/planning/execute.ts) re-checks the write capability, then writeRow (apps/backend/app/services/planning/writer.ts) applies the privacy gate, existence check, prepareEntityWrite from apps/backend/app/services/planning/entity_policy.ts, the working-day gate when the resource changes, and the SQL update.
  12. After image: readStateWithClient again.
  13. NO_CHANGE guard: if the before and after images are semantically equal, the throw rolls the update back.
  14. Restoration guard: a catalogue change to privacy, code name or activity kind that would clear pending restoration groups needs an exact confirmation count. An hours change skips it.
  15. advancePlanningRevision moves the company revision forward once.
  16. The commitment marker is inserted into planning_mutations.
  17. Projection: projectionChanges diffs transformState (from apps/backend/app/transformers/state_transformer.ts) of the active before and after rows, so the patch carries only what this member's role may see.
  18. writeAudit (apps/backend/app/services/audit.ts) records the operation with fields from the projected change. An audit failure rolls back rows, revision and marker together.
  19. The response is { status: 'committed', mutationId, revision, restoration, projection }. withCurrent commits when the callback returns.
  20. Any throw goes through the controller's refusal mapping (next section).

Planning failures ​

CodeHTTPMeaning
VALIDATION_ERROR400Malformed body, route and intent disagree, or a domain rule refused
AUTHORIZATION_DENIED403Role, privacy field, settings access or restoration ownership refused
ACCOUNT_MEMBERSHIP_LOST403No active membership, or the company row is gone
STALE_REVISION409baseRevision is not the current company revision; nothing was written
MUTATION_ID_REUSED409This mutationId already committed; look it up instead of resending
NO_CHANGE400The intent would change nothing; no revision, marker or audit
RESTORATION_CONFIRMATION_REQUIRED409Pending restoration groups would be cleared; body has restorableItemCount
RESTORATION_CONFIRMATION_STALE409The confirmed count no longer matches; body has the new count
No code (conflict and others)409Built-in client, frozen setting or restoration conflict; an error message without a code
MASQUERADE_*403, 409, 428Refused by the view-as middleware before the controller
Account Kit codesKitSession, address or admission refusals (ADMISSION_REQUIRED 403) pass through
No code401No valid session (trusted-local middleware)
None500Unexpected fault; the transaction rolled back

The forwarded codes are listed in planningMutationErrorCodes in apps/backend/app/validators/planning/contracts.ts; any other PlanningOperationError code is sent with its status and no code.

A request that times out or loses its response is not a failure. The browser marks it uncertain, sends nothing new, and asks GET /api/accounts/:accountId/planning/mutations/:mutationId. The answer is committed (with the revision and any restoration handle) or unknown. The lookup is scoped to the same company and actor, so another member always sees unknown. unknown keeps the write uncertain and the editor locked until a later lookup proves commitment or the context changes.

Planning internals other modules import ​

apps/backend/app/services/planning/ is private to the facade and the planning controller, with four deliberate exceptions:

  • errors.ts BatchRequestError: thrown by export import and example data, mapped by their controllers.
  • data_policy.ts BatchCapabilities: the capability type the planning engine consumes.
  • entity_policy.ts TABLE_NAMES: the scoped table list for export import and example data.
  • server_timestamp.ts createServerRevision: row timestamps for anonymisation.

planning_revision.ts and state_repository.ts sit outside the directory on purpose: every product writer advances the revision, and export, import and anonymisation read rows the same way.

Browser ownership ​

One createPlanningCacheController in apps/frontend/src/data/planning/planningCacheController.ts owns the confirmed planning cache, page-local Undo/Redo history (50 entries) and the single pending or uncertain write. The store wires it in apps/frontend/src/store/slices/allocationSlice.ts; nothing else writes planning rows in the browser, and nothing is persisted.

  • apps/frontend/src/data/planning/planningCommands.ts builds intent and inverse pairs from a gesture. A build with no difference returns null and nothing is sent.
  • Two transports implement one interface: HTTP in apps/frontend/src/data/planning/planningTransport.ts and the volatile in-memory demo in apps/frontend/src/data/planning/volatilePlanningTransport.ts, which reproduces the server's revision, idempotency, refusal and lookup behaviour.
  • Wire types come from the generated Tuyau route registry through apps/frontend/src/api/planningContracts.ts. They are type aliases only; the backend Vine validators are the only runtime schema.

Which tests establish which guarantee ​

Backend test paths are relative to apps/backend/.

  • Authority. tests/functional/planning/operations.spec.ts (Viewer and route mismatches), tests/functional/auth/native_authorization.spec.ts (four-role matrix, next-transaction role changes), tests/functional/auth/password_sessions.spec.ts (revocation between admission and write), tests/functional/auth/admission.spec.ts, tests/functional/auth/invitations.spec.ts, tests/functional/membership/ownership_transfer.spec.ts, tests/functional/privacy/password_confirmation_bindings.spec.ts (password confirmation bindings).
  • Tenant isolation. tests/functional/planning/tenant_bulk.spec.ts (bulk intents change only the caller's company), tests/functional/data_routes.spec.ts (export stays in one company), tests/functional/membership/control_data_isolation.spec.ts, tests/unit/tenant_scope.spec.ts.
  • Atomicity and rollback. tests/functional/planning/transactions.spec.ts (audit failure rolls back rows, revision and marker; competing drafts commit once), tests/functional/planning/availability.spec.ts (group rollback), tests/functional/transfer_apply.spec.ts, tests/functional/anonymise.spec.ts, tests/functional/auth/first_company_setup.spec.ts, tests/functional/transaction_faults.spec.ts (the transaction primitive itself).
  • Idempotency and lookup. tests/functional/planning/http_contract.spec.ts (stale and duplicate identities never commit again; lookup is actor and company scoped), tests/functional/planning/restoration.spec.ts (late duplicates never re-apply), tests/functional/membership/member_administration.spec.ts (command receipt replay).
  • Projection and confidentiality. tests/unit/state_transformer.spec.ts, tests/functional/planning/archive_recovery.spec.ts, tests/functional/planning/operations.spec.ts (confidential values preserved for Editors), tests/functional/auth/masquerade.spec.ts (target role for reads, real actor for audit).
  • Recovery. tests/functional/planning/restoration.spec.ts, tests/functional/planning/retained_restoration.spec.ts, tests/unit/backup_provider.spec.ts, tests/unit/upgrade_command.spec.ts, tests/unit/app_reset_command.spec.ts, tests/unit/owner_reset_command.spec.ts, tests/unit/company_initialize_command.spec.ts.
  • Browser coordinator. The frontend files listed under Browser ownership, plus e2e/planning-controller.auth.spec.ts and e2e/scheduler-persistence.auth.spec.ts, which drive real typed routes against SQLite.
